# netcup Legacy DNS boundary

Assessed **2026-10-20** from the official [Legacy API guide](https://www.netcup.com/en/helpcenter/documentation/domain/our-api) and [DomainWebservice types](https://ccp.netcup.net/run/webservice/servers/endpoint.php).

Legacy DNS is separate from SCP and CloudDNS. Its JSON endpoint is exactly `https://ccp.netcup.net/run/webservice/servers/endpoint.php?JSON`. The `netcup_legacy_v1` credential binds customer number, Legacy API key and Legacy API password to one connection/version. A successful login establishes a session, but its response contains no native customer identity and proves no zone permission. The shared connection contract requires provider-derived identity, so candidate validation returns identity-unverified rather than echoing the submitted customer number as verified metadata. Sessions expire after 15 idle minutes. The candidate adapter serializes acquisition and reads, uses a conservative 14-minute absolute lifetime, invalidates a rejected session and never replays a failed JSON POST. Native client errors stay generic; HTTP 401/403 are permission denials. There is no SCP/SOAP fallback or ambient credential lookup.

Only login, `infoDnsZone` and `infoDnsRecords` are allowed. Reads are limited to an explicitly selected zone, the shared byte/deadline/connection budget and 2,000 records. The optional shared DNS read port projects allowlisted zone/record facts separately from compute inventory. There is no reseller enumeration or purchase path. Names use ASCII DNS labels (IDNs must already be punycoded). Record sets group name/type with zone-level TTL and preserve unknown types. Known types follow the official [simple-type XSD](https://ccp.netcup.net/run/webservice/xsd/simpletypes.xsd); type recognition is not permission or write support. Legacy immutability remains unknown. A serial check before and after records rejects visibly torn reads. It does not provide atomic snapshot isolation. Native serial and a scoped fingerprint are read evidence only.

The documented update signature has no expected serial or conditional-write precondition; the zone serial is read-only. The official [WSDL](https://ccp.netcup.net/run/webservice/servers/endpoint.php?WSDL) likewise exposes domain, customer, API key, session, client request ID and record set, with no expected version. Its linked [type schema](https://ccp.netcup.net/run/webservice/xsd/complextypes.xsd) confirms that `Dnsrecordset` contains only records, and individual records have no expected-version member. This establishes that an expected-serial argument cannot be expressed through the published call. It does not establish that all provider APIs or undocumented atomic record-matching guarantees are unsupported. Matching local hashes cannot prevent a concurrent edit after a read. `CheckWrite` therefore rejects even a fresh snapshot. SAMA-144 needs a proven native concurrency guarantee or an explicit design decision, followed by action-specific disposable acceptance, before any mutation is implemented or exposed. A client request ID is not proof of idempotency or conflict protection.

The candidate is not registered in runtime validation, inventory or action factories. Provider-derived customer identity, qualified DNS persistence/application projection and explicit disposable read acceptance remain required before backoffice exposure. The read port and synthetic fixtures do not establish those gates. No live account or DNS operation was used to establish this contract.
