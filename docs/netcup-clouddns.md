# netcup CloudDNS qualification

Assessed **2026-10-20** from the official [netcup API guide](https://www.netcup.com/en/helpcenter/documentation/general/netcup-api), [CloudDNS guide](https://www.netcup.com/en/helpcenter/documentation/domain/cloud-dns) and [technical schema](https://www.netcup.com/en/helpcenter/documentation/netcup-api). CloudDNS has its own CCP API key; Legacy DNS and SCP credentials are separate.

The published OpenAPI schema is `netcup API` version `2026.0921.153936`, with absolute origin `https://api.netcup.com`. Its decoded SHA-256 is `e46993ebca985d802328a6a18d486ca3f4996879ef97e3d512a6490e09935bd9`. Domain operations reference `bearerAuth`, but the published components omit the scheme definition. The omissions also occur in the [documentation's source JSON](https://www.netcup.com/api/v2/content/helpcenter/documentation/netcup-api). The schema has no account/current-customer endpoint, credential expiry contract or returned customer identity. A conventional header name or a domain ID is insufficient evidence of connection account identity. These are unavailable contracts in the inspected material, not proof that the provider cannot support authentication or customer identity. SAMA-145 remains gated; there is no credential-bearing CloudDNS client or runtime registration.

## Read contract prepared for qualification

The schema documents domain list, revision list/get and revision-record list/get. Domain objects contain `id`, `fqdn`, `isDnsManaged`. Revision objects contain `identifier`, timestamps, an unenumerated `state`, and nullable `serial`. DNS records contain `identifier`, `name`, `type`, `rdata`, nullable `ttl`, and `immutable`.

The separate `DnsRecordInput` write schema explicitly describes relative names, `@` for the apex and `*` for a wildcard label; `rdata` uses zone-file format and write TTL has a minimum of 1. These input rules do not by themselves prove the response owner-name convention or how a nullable read TTL resolves. An explicit zero in a read fixture is not a valid write TTL under that input contract.

The offline read decoder binds an already-authorized domain and revision to one workspace/connection/version. It bounds bytes and records, checks complete pagination evidence, groups owner/type, preserves nullable TTL as unknown, accepts explicit zero read TTL and retains unfamiliar types. The shared read model keeps native immutability separate from type recognition; neither field grants action permission. No inheritance meaning is assigned to null without a contract. It does not select a current revision from an invented state vocabulary, fetch endpoints, grant permissions or establish account ownership. Full SAMA-146 acceptance requires the qualified identity/transport, native name/state semantics, authorized revision selection and disposable read evidence.

## Mutation and UI gates

The schema documents revision creation, record changes and revision commit. Both domain and revision changesets take `autoCommit` and `strict` booleans plus optional create/delete record lists. The schema explains accepted boolean encodings, but not what `strict` guarantees, whether a changeset is atomic, or how a stale revision is rejected at commit. It documents no conditional header or expected-current-revision argument. This is missing concurrency evidence, not a demonstration that conflict protection is unsupported: `strict` may have relevant semantics that need an authoritative explanation. A revision identifier and a fresh local fingerprint alone cannot prove protection against concurrent edits. SAMA-147 therefore stays blocked at the shared DNS write gate; no mutation request is implemented.

SAMA-148 requires qualified DNS families and the existing server-held review/confirmation boundary. Neither DNS family has external acceptance or a safe mutation contract yet, so the backoffice exposes no new DNS controls. The eventual typed review must show zone, owner, type, TTL source and changed values; distinguish permission denial from unsupported/immutable types; and require a refreshed review after conflicts. No browser-only preview or confirmation bypass substitutes for that boundary.

Before enablement: establish official auth/header and customer identity, scopes/expiry, current-revision/name semantics, complete read traversal and native conflict guarantees. Then perform explicitly authorized disposable reads and action-specific write/recovery acceptance. No live provider operation was performed for this assessment.
